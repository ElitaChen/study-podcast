# S5.7: APIs as Contracts

About 11 minutes.

## Where we left off

Last time, permissions, privacy and identity. Today, the agreements that hold a system together. Every time one part of a system talks to another, the client to the server, one team's service to another's, an app to the operating system, there is an API in between. Understanding APIs as contracts helps designers see why some changes are easy and others are surprisingly hard.

## The bottom line

An API is a contract: a promise about what you can ask for, what you must provide, and what you will get back. Contracts let teams work independently, but they also lock in decisions, because changing a contract can break everyone who relies on it. Designers meet APIs everywhere: in what a screen can show, in what the system lets apps do, and increasingly in what AI agents can do. Good API design is a lot like good interface design, for a different user.

## What an API is

API stands for application programming interface. It is the interface software uses to talk to other software.

A simple example. The weather app asks a weather service: give me the forecast for this city. The service answers with temperature, conditions and times, in a fixed format.

The API defines the question, what you must send, like the city, and the answer, what fields come back. Neither side needs to know how the other works inside. That separation is the whole point.

## Contracts let teams move independently

In a large company, dozens of teams build parts of a product. The calendar team, the notifications team, the AI team. Each exposes APIs to the others.

As long as everyone keeps their contracts, teams can change their internals freely. The calendar team can rebuild its whole storage system, and nobody else notices, if the API stays the same.

This is why APIs are so valuable. And it is why changing them is so expensive.

## Why changes are hard

Imagine the calendar API returns an event with one location field. The design team wants events to support several locations, an office and a video link.

Changing location from one value to a list breaks every client that expects one value. Old app versions crash or show nothing. Other teams' features break.

So engineers usually add instead of change. Keep the old location field, and add a new field, locations, as a list. Old clients keep working. New clients use the new field. This is called backward compatibility.

For designers, it explains a common frustration: why does the data seem to have duplicate, awkward fields? Often because the system grew by adding, never removing, to keep old contracts working.

Take a moment. In your own words, why do engineers add new fields instead of changing old ones?

## Designing the contract is design work

An API has a user: the developer who calls it. And like any interface, it can be clear or confusing.

Good APIs have consistent naming, predictable behavior, clear errors, and sensible defaults. Bad ones have fields named differently for the same thing, surprising side effects, and error messages that explain nothing.

That sounds familiar. It is the same set of qualities you care about in a design system. Consistent names, clear components, documented behavior. In fact, the component contracts from S2 are close relatives of APIs: both say what something is for, what it needs, and what it promises.

## Errors are part of the contract

A strong contract says not only what happens when things go right, but what happens when they go wrong.

The event was not found. You do not have permission. The service is overloaded, try later. The time you asked for is invalid.

Each of these errors eventually becomes something a user experiences. If the API returns a vague error, the app can only show a vague message. If it returns a specific one, the app can show something helpful. Your meeting could not be moved because the room is booked.

So designers have a direct interest in API errors. A short list of the errors a user might face, and what the interface should say for each, is a valuable addition to any spec.

## Worked example one: the system as an API

Apple's App Intents framework, which episode twelve covers, is an API between apps and the operating system. An app describes the actions it can do and the things it contains, and the system can then offer them in Siri, Spotlight, widgets and Shortcuts.

A designer on an app team effectively designs this contract. Which actions to expose, with which names and parameters, and what each returns. Get it right, and the app's features appear naturally across the system. Get it wrong, and Siri offers confusingly named actions that fail half the time.

This is API design as product design.

## Worked example two: where an API quietly shapes the experience

A team designs a feature showing the status of a package: ordered, shipped, out for delivery, delivered.

The shipping partner's API only reports two states: in transit and delivered. No out for delivery.

The design shows four steps, but two are never filled. The progress bar jumps from shipped straight to delivered. Users wonder why it skipped.

The contract with an outside partner limited the experience. The fix is to design from the data you actually get, or negotiate for a richer contract. Either way, the API had to be read before the screens were designed.

## Going deeper: APIs for AI agents

Agents use APIs too. In B1 and B3, tool use and MCP are API contracts written for models instead of developers.

That changes some design priorities. A human developer reads documentation once and remembers it. A model reads the tool description every time, and acts on it literally. So descriptions must be precise, names must be unambiguous, and errors must explain what to do next, because the model will try to recover based on what the error says.

A 2026 trend in agent design is that the same capabilities get exposed several ways: as an API for developers, as tools for agents, as App Intents for the system. Designers who think of capabilities as contracts can keep these consistent, so the same action means the same thing everywhere.

## The strongest counterargument

The best case against designers engaging with APIs: they are owned by engineering, and designers rarely have the context to judge performance, security or versioning trade offs.

True for those trade offs. But naming, consistency, error meaning, and which capabilities to expose are experience questions. Many API problems that hurt users are really naming and modeling problems, which designers are trained to see.

## Practice scenario

Your team wants to let other apps and AI agents create reminders in your app.

Your question. What would the contract need: what inputs are required, what is optional, what comes back, and which errors should be possible? How would the same action appear as an API, an agent tool, and a system shortcut?

## The product implications

Three things to take away.

One. An API is a contract. It lets teams move independently and locks in decisions.

Two. Changing contracts is expensive, so systems grow by adding. Ask for contract changes early.

Three. Naming, consistency and errors in APIs are experience design, for developers, agents and ultimately users.
