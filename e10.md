# S5.10: Defaults and Settings as System Design

About 11 minutes.

## Where we left off

Last time, feature collisions and resolution strategies. Today, the quietest but most powerful lever in any system: defaults. The value a setting has before anyone touches it. For most people, the default is the product.

## The bottom line

People strongly tend to stay with whatever option is preselected. A large meta analysis found the effect is real and substantial, but varies a lot depending on context and on how the default is perceived. Every default is therefore a design decision with large effects, and settings are not a place to dump decisions the team could not make. In system design terms, defaults define how the system behaves for most people, most of the time.

## The default effect

When an option is preselected, people are more likely to end up with it. This is one of the best known findings in behavioral science.

The most famous example comes from organ donation. In a 2003 study, Eric Johnson and Daniel Goldstein showed that countries where donation was the default, with an opt out, had far higher consent rates than countries where people had to opt in.

## How strong is it really

In 2019, Jon Jachimowicz, Shannon Duncan, Elke Weber and Eric Johnson published a meta analysis in the journal Behavioural Public Policy. They combined fifty eight studies, with more than seventy three thousand participants in total.

The headline: defaults have a considerable effect. In a summary for a general audience, the authors described it this way: in decisions with two options, the preselected one is chosen about twenty seven percent more often.

But the more interesting finding was the variation. Most studies found positive effects. Several found no significant effect. Two even found negative effects. So defaults are powerful, but not a magic switch.

## Why defaults work

The authors drew on a framework with three reasons, sometimes called the three Es.

Endorsement. People read the default as a recommendation. The designers must think this is best.

Ease. Changing it takes effort. Staying is free.

Endowment. People feel the default is already theirs, and giving it up feels like a loss.

They found that defaults work better when they are seen as endorsement or endowment. They also found defaults were more effective in consumer settings, and less effective in environmental ones. And other researchers point out that when people's preferences vary a lot, a single default suits fewer of them.

## What this means for product design

Three implications.

First, the default is the experience for most people. If a notification setting defaults to on, most people will get notifications, whether or not they would have chosen them. Design for the default, not for the settings screen.

Second, users read defaults as advice. So a default that serves the company more than the user, like sharing data by default, uses the user's trust against them. That is a design ethics question, not just a growth tactic.

Third, a settings screen is not a solution to a decision the team avoided. Adding a toggle because the team could not agree means most users get whatever the default happens to be, which nobody actually decided on purpose.

## Settings as a system

## Smart defaults

A modern pattern is the context aware default: the starting value depends on the situation. A video app defaults to lower quality on mobile data. A keyboard defaults to the language you last used with this person.

Smart defaults can be wonderful. But they make behavior less predictable. Users may not know why the value changed. The trust tools from B5 apply: show why, when it matters, and make it easy to set a fixed preference.

## Worked example one: an assistant's proactivity

A team adds proactive suggestions to an assistant. A new setting: suggestions on or off.

Default on: most users get suggestions. Usage metrics rise. Dismissal rates may also rise. Some users are annoyed but never find the setting.

Default off: few users ever discover suggestions. The feature looks like a failure.

Better: a middle default. Start with a small number of high confidence suggestions, at passive urgency from S5. Measure dismissal, from M2's guardrails. Ask once, after a few useful suggestions, whether the user wants more or fewer. The default becomes a starting point that adapts, with the user's consent.

## Worked example two: where a default does harm quietly

A photo app defaults to including location data when sharing photos. Most users never change it. Most never realize photos they share reveal where they live.

Nobody made a malicious choice. An engineer set the default early, because it was simplest. It was never revisited.

This is the system design lesson: defaults are often set by accident, early, and then become permanent behavior for millions of people. A periodic review of defaults, asking who chose this, and does it still serve users, is one of the most valuable audits a designer can lead.

## Going deeper: defaults for AI behavior

AI features have defaults too, often hidden. How long should answers be? How formal? Should the assistant act or ask? Should it show sources?

These live in system prompts and configuration, not settings screens. But they work exactly like defaults: most users never change them, and read them as the product's intended behavior.

So the spec should name them. Default answer length. Default confirmation level. Default visibility of reasoning. Each one is a decision with the same power as any visible setting.

## The strongest counterargument

The best case against powerful defaults: they are paternalistic. Choosing for people, even with good intentions, takes away their agency. Better to make everyone choose actively.

There is a real tradeoff. Some researchers have raised concerns about autonomy and welfare in default nudges. But forced choice for everything overwhelms people, and every product needs some starting state. The fair answer is transparency and reversibility: choose defaults that serve users, make them easy to see and change, and never use them to extract value people would not knowingly give.

## The product implications

Three things to take away.

One. Defaults are the experience for most people, and users read them as advice.

Two. The effect is strong but varies. Design defaults on purpose, and review the accidental ones.

Three. AI behavior has hidden defaults too. Name them in the spec.
