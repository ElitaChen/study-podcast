# S5.8: Where AI Sits in the Architecture

## Where we left off

## The bottom line

AI can run on the device, on a private cloud designed for privacy, or on a third party server. Each place has different strengths: speed, privacy, capability and cost. Modern apps increasingly route each task to the right place. For designers, this routing decides what features are possible offline, how private they are, how fast they feel, and how they fail. In 2026, Apple's Foundation Models framework made this routing concrete for app developers.

## Three places a model can run

On the device. A smaller model runs directly on the phone or computer. Fast, private, works offline, and free per use. But less capable, with a smaller context.

On a private cloud. A larger model runs on servers designed so the provider cannot see the data. Apple calls this Private Cloud Compute. More capable, still strongly private, but needs a network.

On a third party server. A frontier model from another company, through an API. Most capable for hard tasks. But data leaves the platform's privacy boundary, it costs money per use, and it depends on another company's service.

## What Apple shipped

Apple introduced the Foundation Models framework at WWDC 2025, available with iOS 26. It gave app developers direct access to the on device model behind Apple Intelligence, about three billion parameters, in Apple's own description. Independent write ups of the framework report that the on device model has a context of around four thousand tokens, shared between the prompt and the response.

At WWDC 2026, Apple expanded it. According to Apple's developer documentation and press coverage, the framework can now route work to Private Cloud Compute, with a much larger context, reported at around thirty two thousand tokens. It added image input. And it allows other model providers, such as Claude and Gemini, to plug in through a common interface. Apple also announced that developers with fewer than two million first time App Store downloads can use the Private Cloud Compute models with no cloud API cost.

Details change quickly, so check Apple's current documentation before relying on specifics. But the shape is what matters for design: one framework, several places to run, chosen per task.

## Routing: the right model for each task

Routing means deciding, for each request, which model handles it.

Short, simple, private tasks, like classifying a note or suggesting a title: on device. Instant, offline, nothing leaves the phone.

Longer tasks with more context, like summarizing a long document: private cloud.

Hard reasoning or specialized knowledge: a frontier model, if the user's data and consent allow it.

This is R1's effort routing at the architecture level. Fast by default, more power when the task needs it.

## Why routing is an experience decision

Each route changes the experience in ways users feel.

Offline: on device features keep working in the subway. Cloud features do not.

Privacy: users may accept on device processing of their messages, but not sending them to another company.

Speed: on device can be near instant. Cloud adds network latency, and reasoning adds more.

Quality: the small model may give weaker answers on hard tasks.

So the same feature may behave differently depending on the route. A designer must decide what the user sees and knows about that.

## Cost changes design

On a third party server, every request costs money. That shapes design in ways that are easy to miss.

Features that call the model on every keystroke can become very expensive. Features that generate long answers by default cost more than short ones. Proactive features, where the AI acts without being asked, multiply calls for every user.

This is why M2 included cost per completed task as a guardrail. And why on device models matter: they make some features economically possible that would be too expensive in the cloud.

## Fallbacks: when the model fails

Models fail in architectural ways, not just quality ways. The device is too old to run the on device model. The network is down, so cloud models are unreachable. The provider is overloaded. The context is too long for the small model. Safety systems decline the request.

Each needs a designed fallback.

Use a smaller model with a simpler result.

Offer the non AI version of the feature.

Queue the task and finish later, with a notification.

Or explain clearly what is unavailable and why.

The worst fallback is silence, or a generic error, which leaves people unsure whether to wait, retry, or give up.

## Worked example one: a smart reply feature

Default: the on device model suggests short replies. Instant, private, offline.

If the message is long or complex: route to the private cloud for better suggestions, with a brief working state.

If the device cannot run the on device model: use the private cloud when online, and hide suggestions offline, without an error.

Privacy: no message ever goes to a third party without the user explicitly choosing a feature that says so.

Spec note: suggestions from different routes should look and behave the same, so users are not confused by visible differences in quality between moments.

## Worked example two: where routing surprises users

An app summarizes meeting notes. On a new phone, summaries are rich and detailed, from the cloud model. On the same user's older iPad, the app falls back to a smaller model, and summaries are short and miss key points.

The user thinks the feature is broken on the iPad. They do not know about routing. And they compare the two and trust neither.

Options: tell the user when a lighter mode is in use, in plain words. Or keep quality consistent by always using the cloud, at a cost to offline use. Or do not offer the feature where quality would be too low. Each is valid. Not deciding is the failure.

## Going deeper: the model as one component

A useful mental shift. In a well designed system, the model is one component among many, not the center. Retrieval from R3, data models from episode two, permissions from episode six, contracts from episode seven, sync from episode three. The model only sees what the rest of the system gives it, and can only do what the system allows.

So most of the design leverage around AI is still in the system: what context is assembled, what tools exist, where results are stored, how they sync, and how failures surface. That is A3's product layer, now seen as architecture.

## The strongest counterargument

The best case against designers engaging with routing: it is a fast changing engineering and business decision about vendors, costs and contracts. Designers cannot keep up, and the decision will be made on cost anyway.

Often true. But the consequences are experience consequences: offline behavior, privacy, speed, and quality consistency. Designers can define those requirements clearly, so whatever route is chosen, the experience holds.

## The product implications

Three things to take away.

One. Models can run on device, on a private cloud, or on a third party server, each with different speed, privacy, capability and cost.

Two. Routing is an experience decision. Specify offline behavior, privacy boundaries and quality consistency.

Three. Design fallbacks for every way the model can be unavailable. Never fail silently.
