# R3: Why Retrieval Fails

About 12 minutes.

## Where we left off

Last time, scaling laws and the data wall. Today we go back to grounding, and its most common weak spot.

In A6, retrieval was the second form of grounding. The product searches a large set of documents, picks the most relevant pieces, and puts them in the model's context. The model answers from those pieces. Simple in principle. In practice, this is where many AI features quietly break.

## The bottom line

In retrieval, the model can only be as good as the passages it is handed. Many failures that look like the model making things up actually start earlier, when the search found the wrong piece, missed the right one, or cut it in a bad place. In 2026, the industry has largely converged on a fix: combine two kinds of search, then rerank. And for harder questions, let an agent search in several rounds.

## Failures that look like model failures

A useful way to see this comes from a July 2026 article in The New Stack about agent architecture. Its central point: many failures that look like language model problems start in the step where context is built.

Think about what that means. The user sees a confident wrong answer and blames the model for hallucinating. But if you trace what happened, the right document never made it into the context. The model did its best with what it got.

So the first rule of retrieval: before blaming the model, check what it was given.

## Four places retrieval breaks

One. Chunking. Before searching, documents are split into pieces called chunks. If a split falls in the middle of an idea, half the answer sits in one chunk, half in another. Neither looks relevant enough on its own, so neither gets picked.

Two. Matching by meaning. Most retrieval uses embeddings, from A4. Chunks whose meaning sits close to the question are chosen. But close in meaning is not the same as useful. A passage that repeats the question's words without answering it can rank above the passage that actually answers.

Three. Missing exact terms. Embedding search is weak with exact names, product codes, error numbers, and version labels. Heart attack and cardiac arrest land near each other in meaning space, which is helpful. But a question about version seventeen point two may retrieve a passage about seventeen point one, because they look almost identical in meaning.

Four. Freshness and conflicts. Old and new versions of a document can both be found. The model may use the old one, or blend the two into something neither says.

## What the industry converged on

Through 2025, many companies built retrieval with embedding search alone. In 2026, there was what VentureBeat called a retrieval rebuild. Enterprises that had scaled quickly hit quality problems, and the consensus answer became hybrid retrieval.

Hybrid retrieval combines two kinds of search. Dense search, using embeddings, catches meaning even when words differ. Sparse search, an older keyword method often called BM25, catches exact terms, names, and codes. Together, they cover each other's blind spots.

Then comes reranking. Instead of taking the top five results directly, the system retrieves a larger set, maybe twenty to fifty candidates, then uses a second, more careful model to reorder them by real usefulness, and keeps the best few.

How much does this help? Anthropic published research in 2024 on a method called contextual retrieval, which adds a short description of the surrounding document to each chunk before indexing it. According to secondary reports of that research, contextual embeddings alone cut retrieval failures by about a third. Adding keyword search brought the reduction to about half. Adding reranking brought it to about two thirds. Treat the exact numbers carefully, since they come from one set of tests, but the direction has been confirmed by many teams since.

## When one search is not enough

Some questions cannot be answered with a single search. Which of our three design system components changed most since the last release, and what broke because of it? That needs one search to find the changes, another to find the bugs, and a step to connect them.

This is where agentic retrieval comes in. An agent decides what to search, looks at what it found, judges whether it is enough, and searches again if needed. It is the tool use loop from B1, applied to search.

But here is an important finding from 2026 practice. A Towards Data Science article argued that agentic systems still perform better when built on top of strong basic retrieval. An agent searching a weak index just fails more times, more expensively. The authors' advice was to earn complexity: start with simple search, add hybrid and reranking when you see failures, and add agentic search only when questions truly need multiple steps.

## Context rot

One more failure deserves a name. When retrieval is weak, a common reaction is to retrieve more chunks, just in case. Twenty instead of five. Fifty instead of twenty.

This creates what practitioners now call context rot. The context fills with noisy, half relevant material. Remember A4: attention spreads across everything in the context. More noise means less weight on the passage that matters. Retrieving more can make answers worse.

## Worked example one: a help assistant

A user asks the system help assistant: how do I turn off the new focus filter?

With embedding search alone: it finds an article about a similar filter from an older version. The model explains confidently, with steps that no longer exist. The user follows them, fails, and loses trust.

With the 2026 approach: keyword search catches the exact feature name. Version metadata, a date and release tag attached to each document, lets the system prefer the current release. Reranking pushes the right article to the top. And the answer shows its source, with the version, so if anything still looks off, the user can see why.

## Worked example two: where better retrieval does not help

Now a different failure. The user asks: is it safe to turn off this privacy setting?

Retrieval finds exactly the right article. But the article itself is vague. It describes what the setting does, not the trade offs. The model, asked for a judgment, fills the gap with a confident opinion.

No retrieval improvement fixes this. The problem is the content. Which brings us to the designer's most underrated lever.

## Content design is retrieval design

Documents written with clear headings, one idea per section, stable names, and explicit trade offs are far easier to retrieve and to answer from. Documents with long mixed sections, renamed features, and vague language are hard.

This makes writing for retrieval a new kind of information architecture. The ontology from S3, the stable vocabulary from S7, and clear sectioning all directly improve AI answer quality. For a designer with IA skills, this is a place to contribute that engineers often overlook.

## The strongest counterargument

The best case against designers caring about retrieval: it is infrastructure. Search algorithms, indexes, rerankers. Engineering work.

The response: the algorithms are engineering, yes. But three things in retrieval are design. What the user sees about sources. What happens when sources conflict or nothing is found. And how the content itself is structured. Those three decide whether retrieval failures are invisible or catchable.

## The product implications

Three things to take away.

One. Many errors that look like hallucination are retrieval errors. Check what the model was given before blaming it.

Two. Hybrid search plus reranking is the 2026 baseline. Agentic search helps for multi step questions, but only on top of strong basic retrieval.

Three. Sources, conflicts, not knowing, and content structure are design surfaces. Writing for retrieval is information architecture.
