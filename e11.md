# S5.11: How Failure Spreads

About 11 minutes.

## Where we left off

Last time, defaults and settings. Today, the darker side of systems. In a connected system, failure rarely stays where it starts. A slow service makes another slow, a missing value breaks a screen, a retry storm takes down a server. Designers usually see only the final symptom. Seeing the chain helps you design experiences that bend instead of break.

## The bottom line

Failures spread through dependencies. When one part fails, everything that relies on it can fail too, unless the system is designed to contain it. Engineers have patterns for containment: timeouts, fallbacks, retries with limits, and isolating parts so one failure cannot take down others. Each pattern has an experience counterpart that designers should specify: what the user sees when a part is down, how much of the feature still works, and how recovery feels.

## Dependencies: the hidden map

Every feature depends on other things. A screen showing your upcoming trip may depend on the calendar service, the email parsing service, a maps service for travel time, a weather service, and an AI summary.

If all five work, the screen is rich. If one fails, what happens? In a fragile design, the whole screen shows an error. In a resilient design, the screen shows four parts, and a quiet note where the fifth would be.

The difference is not luck. It comes from knowing the dependencies and deciding, for each, what happens when it fails.

## Cascades

A cascade is when one failure triggers others.

A simple version. The weather service becomes slow. The trip screen waits for it. Users get impatient and refresh. Each refresh sends more requests. The weather service gets even slower under the extra load. Now the trip screen times out for everyone, even though only weather had a problem.

Notice the role of user behavior. People retrying is natural. A system that does not expect it can turn a small slowdown into a full outage.

Take a moment. In your own words, explain how a small slowdown in one service can become a failure everywhere.

## Engineering patterns, and their design twins

Timeouts. Stop waiting for a slow part after a set time. Design twin: decide what the screen shows when that part times out. A placeholder, a cached value, or nothing.

Fallbacks. Use a simpler alternative when the main path fails. Design twin: specify the alternative. Show yesterday's weather with a label, or hide the weather card entirely.

Retries with limits. Try again, but not forever, and wait a bit longer each time. Design twin: do not encourage users to hammer the retry button. After a failure, show when the system will try again on its own.

Isolation. Separate parts so one cannot drag down others. Design twin: layouts where each section loads and fails independently. Sometimes called graceful degradation.

Circuit breakers. If a dependency keeps failing, stop calling it for a while, and use the fallback immediately. Design twin: once a part is known to be down, stop showing loading states for it. Show the degraded version right away, so people are not left waiting for something that will not come.

## Partial success

Many actions involve several steps across services. Move five meetings. Share an album with four people. Save a document and update its index.

What if three of five succeed? This is partial success, and it is one of the most under designed states in software.

The spec should answer: are the successful steps kept or undone? Does the user see exactly which steps failed? Can they retry only the failed ones? You met this in P4, partial work. At system level, it becomes a core question for any multi step action, especially those done by agents.

## Worked example one: a resilient trip screen

Dependencies: calendar, email, maps, weather, AI summary.

Calendar fails: this is the core. Show a clear error, with cached trip data if available, labeled as possibly out of date.

Email parsing fails: show the trip without imported bookings, with a line saying some bookings could not be loaded.

Maps fails: hide travel time, keep the rest.

Weather fails: hide the weather card. No error message needed.

AI summary fails: show the raw details instead of the summary.

Each dependency has a designed failure, proportional to its importance. The screen bends. It does not break.

## Worked example two: where a fallback misleads

A banking app's balance service fails. The fallback shows the last cached balance, without a label. A user sees money that has already been spent, and makes a payment that overdraws the account.

The fallback kept the screen working, but showed stale data as if it were current. In domains where freshness matters, a fallback must say clearly that it is old. Or not show the value at all.

So fallbacks are not automatically good. A fallback that hides failure can be worse than an honest error. The design rule: degrade visibly when accuracy matters, quietly when it does not.

## Going deeper: AI as a dependency

AI features add a dependency that fails in unusual ways. It can be slow. It can be unavailable. It can decline. And it can succeed technically while being wrong.

That last one is new. Traditional dependencies either work or fail. A model can return a confident, well formatted, incorrect answer, and nothing in the system notices. That is why S6 introduced checks on generated output, and why grounding and sources matter.

For system resilience, treat the model like any other dependency, plus one more layer. Timeouts, fallbacks and isolation, yes. And also checks on the output before it is shown or acted on, especially for actions.

Agents raise this further. An agent calling five tools is a chain of five dependencies, plus the model's own judgment at every step. A failure halfway, or a wrong step that looks like success, can cascade into later steps. That is why the action records and review moments from P2 and P4 matter so much for agents.

## Designers' contribution

You do not need to build circuit breakers. But you can do three things.

Map dependencies for the features you design. Ask engineers which services each screen relies on.

Rank them. Which are core, without which the feature has no meaning, and which are enhancements?

Specify failure per dependency, proportional to importance. Error for core, quiet degradation for enhancements, and clear labels where staleness matters.

That small table is often missing from specs, and engineers usually welcome it.

## The strongest counterargument

The best case against designing every failure: it multiplies work. A screen with five dependencies has many combinations of partial failure. Designing all of them is impractical.

True. The practical answer is the same as in episode nine: rules instead of cases. A few rules, like core dependencies show errors, enhancements hide quietly, stale values always carry a label, cover most combinations without designing each.

## The product implications

Three things to take away.

One. Failures spread through dependencies. Map them for every feature.

Two. Each engineering resilience pattern has a design twin. Specify timeouts, fallbacks and isolation as experiences.

Three. Degrade visibly when accuracy matters. Treat AI as a dependency that can fail by being wrong.
