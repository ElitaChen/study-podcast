# S5.13: A System Map for One Feature

About 11 minutes.

## Where we left off

Last time, one feature on many surfaces. Today, a practical tool that brings this whole season together: drawing the system around a single feature. Not a company wide diagram. One feature, with everything that touches it, including the parts users never see.

## The bottom line

A feature system map shows four layers: what the user experiences on each surface, the actions and data behind them, the services and dependencies underneath, and the rules and feedback loops that govern behavior over time. Drawing it reveals gaps that screen designs hide: missing states, unclear ownership, collisions, and loops that will reinforce or undermine the feature. It borrows from two traditions you already know: service blueprints from service design, and stocks, flows and feedback loops from systems thinking.

## Two traditions

Service blueprints come from service design. They show a service in layers. What the customer does. What staff do in front of the customer. What happens backstage. And the support processes underneath. A line of visibility separates what customers see from what they do not.

Systems thinking, from Donella Meadows and the units you studied, looks at stocks, flows and feedback loops. A stock is something that accumulates. A flow changes it. A feedback loop is when a stock influences its own flows, either reinforcing change or balancing it.

A feature system map combines them. Blueprint layers for structure. Loops for behavior over time.

## Layer one: experience across surfaces

At the top, everything the user sees and does, on every surface from episode twelve. The app screens, the widget, notifications, voice, Spotlight, the lock screen.

Draw them as one row, not separate flows. That alone often reveals inconsistencies: the widget promises something the app does not show, or a notification leads to a screen that does not exist yet.

## Layer two: actions and data

Below the line of visibility, the capabilities and entities from episodes two and twelve. Which actions does each surface call? Which entities does it read or change?

This layer shows whether surfaces really share one source of truth, or each has its own copy. If two surfaces read different data, they will eventually disagree.

## Layer three: services and dependencies

Below that, the services each action relies on: the app's server, the sync system, the push service, the AI model and its route, third party APIs.

This is the dependency map from episode eleven. Mark each one as core or enhancement. Mark which run on the device and which need the network.

## Layer four: rules and loops

At the bottom, the rules that govern behavior: defaults from episode ten, resolution strategies from episode nine, permissions from episode six, and AI routing from episode eight.

And the feedback loops. This is where systems thinking adds something blueprints miss.

## Finding the loops

Every feature with memory or learning has loops. Finding them early is one of the most valuable things a designer can do.

A reinforcing loop. The assistant suggests actions. Users accept them. The system learns they like suggestions. It suggests more. If suggestions are good, this loop builds value. If they are mediocre, it builds annoyance, and eventually users turn the feature off. Reinforcing loops amplify whatever is already happening.

A balancing loop. Dismissals reduce how often suggestions appear. More dismissals, fewer suggestions. This loop pulls the system toward a stable level that users tolerate.

Good design often pairs a reinforcing loop that creates value with a balancing loop that prevents overshoot. That is exactly what M2's guardrails do, as metrics. On the map, they become visible as structure.

## Stocks worth watching

Some stocks matter for almost every feature.

User trust. It rises slowly with good outcomes and drops fast with bad ones, which U2 described.

Unread items. Notifications, suggestions, inbox. If inflow exceeds what users can process, the stock grows until people give up.

Stored data. Every feature that saves things creates a growing stock that needs search, cleanup and eventually migration.

Drawing these stocks makes long term behavior visible. A feature that looks fine at launch may fail in month six, when a stock has grown too large.

## Worked example one: a proactive suggestions feature

Experience layer: suggestion cards in the app, a widget, occasional notifications.

Actions and data: create suggestion, accept, dismiss. Entities: suggestion, linked to events and documents.

Services: on device model for ranking, cloud model for drafting, calendar and files services, push for notifications.

Rules: default to a small number of suggestions, passive urgency, focus modes respected, assistant actions labeled.

Loops: acceptance increases suggestion frequency, reinforcing. Dismissal decreases it, balancing. Trust as a stock, fed by accepted suggestions, drained by wrong ones.

What the map reveals: the notification and the widget can both show the same suggestion, with no shared state for dismissed. Dismiss it in one place, and it stays in the other. That breaks the balancing loop, because dismissals are not fully counted. A screen design would never have shown this.

## Worked example two: where a map becomes a trap

A team spends three weeks making a beautiful, complete system map of a feature. Every service, every rule, every loop. It hangs on the wall. Nobody uses it.

Maps fail when they become artifacts instead of tools. The point is the questions they raise, not completeness.

Practical rules. Map one feature at a time. Keep it to one page. Start rough, in an hour, with an engineer. Focus on the line of visibility and the loops. And update it only when it answers a question someone is actually asking.

## Going deeper: maps as AI context

There is a newer use for system maps. When a map is written in structured form, it can become context for AI tools. An assistant helping engineers or designers can read which services a feature depends on, which rules apply, and which loops matter.

That connects to your design system work. An AI readable description of a feature's system is the same idea as an AI readable component contract, one level up. Structured, named, and shared.

## The strongest counterargument

The best case against system maps: they quickly go stale. Systems change every sprint, and a map drawn in March is wrong by May. Maintaining it becomes another burden.

True for detailed maps. The answer is to keep them light, focused on structure and loops that change slowly, and to treat them as thinking tools for a decision, not documentation. A stale map that helped make a good decision did its job.

## The product implications

Three things to take away.

One. Map one feature in four layers: experience across surfaces, actions and data, services, and rules and loops.

Two. Find the loops. Pair reinforcing loops that create value with balancing loops that prevent overshoot.

Three. Keep maps light, rough and question driven, or they become wall art.
