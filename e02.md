# S5.2: Data Models, The Objects Behind Every Screen

About 12 minutes.

## Where we left off

Last time, client, server, data, and where state lives. Today we look inside the data. Every screen you design shows some objects, and those objects have a shape defined long before any pixel. That shape is the data model.

## The bottom line

A data model defines the kinds of things in a product, what properties each has, and how they relate. It decides what a design can show and do. If the data model lacks something, no screen can show it. If it shapes something badly, the design will fight it forever. Data models are the engineering side of the ontology from season two, and designers who read them gain a real voice in early decisions.

## Entities, properties, relationships

Three building blocks.

Entities are the kinds of things. An event. A person. A note. A photo.

Properties are what each entity has. An event has a title, a start time, an end time, a location.

Relationships connect entities. An event has attendees, who are people. A note belongs to a folder. A photo can appear in many albums.

You met this in S3 as ontology. The data model is the same idea, written precisely enough for software to store and query it.

## How relationships shape experiences

Relationships come in a few shapes, and each one creates design consequences.

One to one. A user has one profile.

One to many. A folder holds many notes, but each note lives in one folder.

Many to many. A photo can be in many albums, and an album holds many photos.

Now notice the design consequences. If notes can only be in one folder, then moving a note is simple, but a note about two projects has to pick one. If notes can have many tags instead, a note can belong everywhere, but deleting a tag needs a decision: what happens to its notes?

These are design decisions. They are often made by engineers, early, without designers in the room.

Take a moment. In your own words, why does the choice between folders and tags change the experience, not just the storage?

## Identity: what makes something the same thing

A quiet but powerful question. How does the system know two records are the same thing?

If you rename a file, is it the same file? Usually yes: it has an internal ID that does not change. That is why links to it still work.

But consider contacts. Your phone has a contact for Ana from your address book, another from email, another from a messaging app. Are they the same person? The system has to decide, and merging contacts is a famous source of frustration exactly because identity is hard.

For AI features this matters even more. When the assistant says your design review, it must resolve which event that is. Identity is what makes that possible.

## Missing properties make designs impossible

Here is the most practical lesson. If a property does not exist in the data model, no design can show it.

A designer proposes showing who last edited a shared document. Lovely idea. But if the data model never stored the last editor, the feature needs a data change, which may mean migrating millions of existing records. What looked like a small design tweak becomes a project.

So when you design, check: does the data have this? If you are not sure, ask early. It is one of the cheapest questions you can ask, and one of the most expensive to ask late.

## Derived and stored

Some values are stored. Some are calculated when needed.

An event's start time is stored. Whether the event is happening now is derived, calculated from the start time and the current time.

This matters for design because derived values can be slow or impossible to calculate on some surfaces. A widget may not be able to compute something that requires reading thousands of records. A design that relies on a derived value should ask: where and how often is this calculated?

## Worked example one: reading a data model as a designer

Imagine the data model for a reminder. Title. Notes. Due date. Priority, with three values. Completed, true or false. List it belongs to.

A designer reading this can spot questions immediately.

Priority has three fixed values. That is an enum, from B2. Every value needs a label and visual treatment, and no fourth value can appear.

Due date is one field. So there is no start date. A reminder cannot represent a task that spans days. If users want that, it is a data change.

Completed is true or false. So there is no record of when it was completed. A view of what I finished this week is impossible without a new property.

Three design insights, from reading six lines.

## Worked example two: where the data model fights the design

A team designs an AI assistant that can summarize a person's week: meetings, documents, messages, all about the same projects.

The design shows everything grouped by project. Beautiful. But in the data, events have no project property. Documents live in folders that do not match projects. Messages have no link to either.

The assistant has to guess which items belong together. Sometimes it guesses wrong. Users see a confident grouping that mixes two projects.

The design was right about what users need. The data model could not support it. The real fix is upstream: a shared concept, like project or trip, that apps can link to. That is the ontology work from S3, now with a concrete reason to do it.

## Going deeper: when the data model changes

Data models are not fixed forever, but changing them is expensive in a specific way. Imagine you add a new property, completed date, to reminders. What about the millions of reminders completed before the change? They have no date. The design must handle them: show nothing, show an estimate, or label them as completed earlier.

Engineers call this a migration. Every migration creates a period where old and new records live side by side. And with many devices, it gets harder. A user's old iPad may run an older app version that does not know the new property exists. If it edits a reminder, does it erase the completed date by accident?

This is why engineers are careful, and sometimes slow, about data changes. And it is why a small sounding design request can meet surprising resistance. Understanding this helps you in two ways.

First, you can ask for data changes early, bundled with other planned work, when they are cheapest.

Second, you can design for the transition. A spec that says what old records should look like, and what happens on older app versions, is a spec engineers trust. It shows you understand the real system, not just the ideal one.

## How to engage without being an engineer

A few practical habits.

Ask for the data model of features you design. Engineers often have a diagram or a schema. Read it with them.

Bring a list of things users need to see, and check each one against the model.

Name the gaps as experience requirements. Users need to see what they finished this week. Engineering decides how.

And for AI features, check whether the model has the concepts the assistant will talk about. If people ask about projects, the data needs projects.

## The strongest counterargument

The best case against designers working at this level: data models are optimized for things designers do not see, like performance, storage cost and consistency. A model that looks awkward to a designer may be right for good technical reasons.

That is true, and it is why the right posture is questions and requirements, not redesigns. But the opposite failure is far more common: data models designed without anyone asking what users need to see, and then designs forced to fit them for years.

## The product implications

Three things to take away.

One. Data models define entities, properties and relationships. They decide what any design can show.

Two. Missing properties make designs impossible, and data changes are expensive. Ask early.

Three. Read data models with engineers, and turn gaps into experience requirements.
