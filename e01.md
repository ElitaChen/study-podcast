# S5.1: Anatomy of an App, and Where State Lives

About 12 minutes.

## Where we left off

This is season five: systems design for apps and features, for designers. Part one explains how apps work underneath, at the depth a designer needs to reason with engineers and write better specs. Part two is about designing features as systems.

You do not need to build any of this. You need to see it. Because many experiences that look like screen design are actually decided by the system underneath.

## The bottom line

Every app has three places where things happen: the client on the device, the server somewhere else, and the data, with one copy treated as the truth. Where the current truth lives, what engineers call state, decides how fast the app feels, what happens offline, and what people see on their other devices. These are experience decisions, made in architecture. Designers who can ask where state lives can shape them.

## The client

The client is the app on the device. It draws the screens, responds to taps, and keeps some data locally.

The client is close to the user. It responds instantly. It knows things the server does not: that the user is in a subway with no signal, that the screen is small, that the battery is low, that location permission was denied.

But the client is also limited. It can be offline. It can be out of date. And there are many clients: a phone, a tablet, a computer, a watch, each with its own copy of some data.

## The server

The server is a set of computers the company runs elsewhere. It stores shared data, runs heavy logic, and talks to other services. Payments, accounts, shared documents, messages between people.

The server is far from the user. Every request takes time to travel there and back. That travel time is called latency, and it is one of the main reasons apps feel slow.

But the server can see everything at once. It can combine data from many users, enforce rules everyone must follow, and keep a single shared truth.

## The data, and the true copy

Data is the records themselves. A note, a photo, a calendar event, a message.

Usually the same record exists in several places at once. A copy on your phone. A copy on your Mac. A copy on the server. So the important question is not where the data is. It is which copy counts as the truth when they disagree.

## State: the current truth

State is the current condition of something. Is this reminder done or not? Is this message read? What is in the cart right now?

When engineers ask where state lives, they mean: which part of the system holds the truth about this condition, and how do the other parts learn about it?

Take a moment. In your own words, what is the difference between data and state, and why does it matter which copy is the truth?

## Three common patterns

Server as truth. The client asks the server for everything and shows what it returns. Simple and consistent. Every device shows the same thing. But slow, because every action waits for the network, and nearly useless offline. Many banking and shopping features work this way, for good reasons.

Client first, then sync. The client saves changes locally first, shows them immediately, and sends them to the server in the background. Fast, and works offline. But now copies can disagree, and someone has to decide what happens when they do. Notes, reminders and many productivity apps work this way.

Local first. A newer approach that pushes this further. Each device holds a full working copy, and devices merge their changes. A 2026 overview of the approach put it simply: local first means the app works offline and syncs when connected, and the technology has become mature enough to use. Episode three covers this in depth.

## Why designers should care

Each pattern creates a different experience.

Server as truth: spinners, loading states, and clear errors when the network fails. The design work is in waiting and failure.

Client first: instant response, but the possibility of surprises later. A change that seemed saved fails to sync. Two edits collide. The design work is in sync status and conflicts.

These are not visual choices. But they decide what the user experiences more than any color or layout.

## Worked example one: a reminder on two devices

You mark a reminder done on your iPhone in the subway, with no signal. Then you get to the office and open your Mac.

If the app uses server as truth, the iPhone could not even save the change. It should have told you so, clearly.

If it uses client first, the iPhone saved the change locally, and will send it when it reconnects. But on the Mac, the reminder still shows as not done, until the phone syncs. If you mark it done on the Mac too, nothing bad happens. If you edit its title on the Mac while the phone has a different edit waiting, now there is a conflict.

Same feature. Same screens. Completely different experiences, decided by where state lives.

## Worked example two: where the abstraction leaks

A team designs a shared shopping list for families. The designer specifies the screens beautifully. Nobody asks where state lives.

Engineering chooses client first, for speed. Then this happens. Two family members are in different aisles of the same store. Both check off milk. One adds eggs while offline. The list on each phone shows something different for several minutes. One person buys eggs twice.

The screens were fine. The experience failed, because the spec never said what should happen when copies disagree, or how people should see that the list is not yet up to date.

## Going deeper: the cost of the network

It helps to have a feel for the numbers. A tap on the screen that updates something on the device can feel instant, well under a tenth of a second. A request to a server on a good connection often takes a few tenths of a second for the round trip. On a weak mobile connection, it can take seconds. And sometimes it never returns at all.

People notice delays very quickly. A rough rule many teams use: around a tenth of a second feels instant, around one second keeps the flow of thought but feels like waiting, and beyond several seconds people lose focus or assume something broke.

So every time a design waits for the server, it spends from a small budget of patience. A server as truth design spends that budget on every action. A client first design spends it only in the background, where the user does not feel it, but pays later in complexity.

There is also a quiet third cost: battery and data. Apps that constantly ask the server for updates drain both. This is why many apps batch their requests, or wait for the system to tell them something changed. That is episode five.

The practical lesson for a spec: for each important action, say how quickly the user must see a response, and what they should see if the network is slow. That gives engineers a target, without telling them how to build it.

## Questions designers can ask

You do not need technical depth to ask these.

Where does the truth about this live?

What happens if the user does this offline?

How long until other devices see the change?

What does the user see while it is not yet synced?

What happens if two people or two devices change the same thing?

Asking them early, in design review, changes the architecture conversation. Asking them late turns them into bugs.

## The strongest counterargument

The best case against designers learning this: it is engineering territory. Designers who half understand architecture can make bad suggestions, or slow down engineering decisions that should be made by engineers.

That risk is real. The answer is to ask questions and state experience requirements, not to prescribe solutions. Not: use local first. Instead: people must be able to check items off in a store with no signal, and see clearly when the list is not yet up to date. Engineers then choose the architecture that meets that requirement.

## The product implications

Three things to take away.

One. Client, server and data are the three places things happen. State is the current truth, and where it lives shapes the experience.

Two. Server as truth is consistent but slow and fragile offline. Client first is fast but creates sync and conflict problems that need design.

Three. Ask where state lives early, and write experience requirements, not technical prescriptions.
