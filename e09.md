# S5.9: How Features Collide

About 11 minutes.

## Where we left off

Part one explained how apps work as systems underneath. Part two is about designing features as systems. We start with a problem that every growing product meets, and that has been studied for nearly forty years: features that work perfectly alone, and badly together.

## The bottom line

A feature interaction happens when combining two features changes the behavior of one or both. The number of possible interactions grows exponentially with the number of features, so they cannot all be tested or designed one by one. Instead, teams use resolution strategies: general rules that settle whole classes of conflicts. Designing those rules is system design, and it is where coherence across a product is really decided.

## A problem from the telephone age

Feature interaction was first named as a crisis in the telecommunications industry in the late nineteen eighties. Phone companies kept adding features: call waiting, call forwarding, voice mail, calling cards. Each worked. Together, they misbehaved.

A classic example, described in research on telephone switching, involved a calling card and voice mail. Both used the pound key. The calling card feature treated pound as end this call and start another. Voice mail treated pound as a command within the mailbox. When used together, the system could not satisfy both.

Neither feature was broken. The combination was.

## Why it grows so fast

Here is the uncomfortable math. With two features, there is one pair to check. With ten features, there are forty five pairs. And interactions can involve three or more features at once, which only appear when a particular combination is active.

Researchers call this the core of the feature interaction problem: the number of potential interactions to consider grows exponentially with the number of features. One research summary described the result: as features grow, development of new features becomes dominated by analyzing, resolving and verifying interactions.

That sentence describes many large platforms today.

## Collisions in modern products

You see feature interactions every day.

Focus modes and alarms. Does a focus mode silence an alarm? What if the alarm was set by an assistant?

Low power mode and background refresh. A feature promising timely updates quietly stops during low power mode.

Auto lock and a video call. Screen time limits and a work app.

Accessibility settings and a custom design. Large text and a layout that assumed short labels.

And the newest: AI actions and everything else. An assistant that moves a meeting may trigger notifications, change focus schedules, and update a shared calendar that has its own rules.

## Resolution strategies

Since you cannot design every combination, you design rules that settle many at once. Research on feature interaction describes several common strategies.

Priority. Rank features, and when two conflict, the higher one wins. Safety features above convenience. Alarms above focus modes.

Disable a combination. Some features simply cannot be active together. Turning one on turns the other off, with a clear explanation.

Ask the user. When the right answer depends on intent, surface the choice once, and remember it.

Arbitrate per output. Decide, for each shared resource, a rule for who controls it. For example, for sound output: one rule decides which feature may play sound when several want to.

A 2014 study from the University of Waterloo modeled twenty four automotive features and found that only six resolution rules were needed to handle their interactions. Many possible conflicts, few rules. That is the promise of thinking at the level of strategies instead of cases.

## Worked example one: alarms and focus

An assistant can set alarms. Focus modes silence notifications. Sleep mode dims everything.

Without rules, each team decides alone. The result: inconsistent behavior that users cannot predict.

With a resolution strategy. Priority: alarms the user set themselves always sound, in every mode. Alarms created by an assistant inherit the same priority, but only if the user confirmed them. Notifications follow the focus mode. Time sensitive notifications break through only if the focus mode allows them.

Now the behavior is predictable, testable, and explainable in one sentence per rule.

## Worked example two: where a rule backfires

A team sets a simple priority rule: work focus mode silences everything except people on a short list.

Then a family member, not on the list, tries to reach the user during an emergency. The rule silenced them.

The rule was clear, but incomplete. Real systems usually need an escape: repeated calls within a few minutes break through, for example. Resolution strategies must account for rare but important cases. And they must be explained to users, so they can trust the rule and adjust it.

## Why designers should own the rules

Feature interactions are usually discovered by engineers or testers late, as bugs, and fixed one by one. That leads to patchwork behavior.

Designers are in a good position to define the strategies early, because the right resolution depends on what users intend and expect. Engineers can implement priority. Deciding which feature should win, and how to explain it, is an experience decision.

A practical step: for any new feature, list the shared resources it touches. Sound, screen space, notifications, the calendar, battery, the user's attention. Then for each, check which other features touch it, and which rule decides between them.

## Going deeper: AI makes this harder

AI features multiply interactions. An assistant can trigger almost any other feature. It acts on behalf of the user, so other features may treat its actions as if the user did them. And its behavior is not fully predictable, so the combinations it creates are not fully known in advance.

Two principles help.

Treat assistant actions as a distinct source. Other features should know whether the user or the assistant created something, so rules can differ. An alarm the user set is not the same as one an assistant suggested.

And give the assistant the same rules as everyone else. If focus mode silences a notification from an app, it should silence one from the assistant too, unless a rule explicitly says otherwise.

## The strongest counterargument

The best case against centralized rules: they slow teams down. Every new feature must now consider every rule and every other team. Autonomy suffers, and big platforms become bureaucratic.

That cost is real. The alternative, though, is the telephone crisis: each feature fine, the product incoherent. The balance most platforms find is a small set of shared resolution strategies, owned centrally, and full autonomy inside them. A few rules, like the Waterloo study's six, not a review board for every decision.

## The product implications

Three things to take away.

One. Features that work alone can fail together. Interactions grow exponentially with features.

Two. Design resolution strategies, like priority, exclusion, asking, and per resource arbitration, not case by case fixes.

Three. Map shared resources for every new feature, and give assistant actions an explicit place in the rules.
